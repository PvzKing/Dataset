Cara Menulis Commit Message yang Baik

Riwayat Git adalah catatan harian sebuah proyek. Saat bug muncul enam bulan kemudian, commit message yang jelas bisa menghemat berjam-jam penelusuran. Artikel ini merangkum kebiasaan sederhana yang membuat riwayat Git kamu enak dibaca.

Mengapa commit message penting?

Kode menjelaskan apa yang berubah, tetapi jarang menjelaskan mengapa. Commit message adalah tempat terbaik untuk menyimpan alasan itu, karena ia melekat langsung pada perubahan kodenya. Perintah seperti git log, git blame, dan git bisect semuanya bergantung pada riwayat yang bisa dipahami.

Struktur dasar

Commit message yang baik terdiri dari tiga bagian:

  1. Subjek: satu baris ringkas, idealnya maksimal sekitar 50 karakter.
  2. Baris kosong: pemisah antara subjek dan isi.
  3. Isi (opsional): penjelasan alasan dan konteks, dibungkus sekitar 72 karakter per baris.
Perbaiki total belanja yang salah saat diskon 100%

Diskon penuh membuat subtotal bernilai nol, lalu pajak dihitung
dari harga sebelum diskon. Sekarang pajak dihitung setelah diskon
sehingga pesanan gratis tidak lagi terkena pajak.

Gunakan kalimat perintah

Tulis subjek seolah memberi perintah kepada kode: "Tambahkan validasi email", bukan "Menambahkan validasi email" atau "Validasi email sudah ditambahkan". Gaya ini konsisten dengan pesan yang dibuat Git sendiri, misalnya "Merge branch ...".

Jelaskan mengapa, bukan bagaimana

Bagaimana perubahan dibuat sudah terlihat di diff. Isi commit sebaiknya menjawab: masalah apa yang diselesaikan, mengapa pendekatan ini dipilih, dan efek samping apa yang perlu diketahui.

Konvensi Conventional Commits

Banyak tim memakai format Conventional Commits agar riwayat bisa dibaca mesin, misalnya untuk membuat changelog otomatis:

feat: tambahkan pencarian produk
fix: cegah total negatif saat voucher melebihi harga
docs: perbarui panduan instalasi
refactor: pisahkan logika ongkir ke modul sendiri

Prefiks yang umum adalah feat untuk fitur baru, fix untuk perbaikan bug, docs untuk dokumentasi, refactor untuk perubahan struktur tanpa mengubah perilaku, dan test untuk pengujian.

Kesalahan yang sering terjadi

  • Pesan terlalu umum seperti "update", "fix bug", atau "wip".
  • Satu commit berisi banyak perubahan yang tidak berhubungan.
  • Menyebut nama file di subjek padahal sudah terlihat di diff.
  • Menjelaskan kode baris per baris alih-alih alasan perubahannya.
Commit yang kecil dan fokus jauh lebih mudah ditinjau, dibatalkan, dan dipahami daripada satu commit raksasa.

Penutup

Kamu tidak perlu menerapkan semuanya sekaligus. Mulailah dari subjek yang jelas dan berbentuk perintah, lalu biasakan menulis satu atau dua kalimat alasan untuk perubahan yang tidak sepele. Rekan setim, dan dirimu sendiri di masa depan, akan berterima kasih.
